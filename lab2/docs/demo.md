## Задание 2.7 — MQTT

1. Открыть вкладку **«2.7 — MQTT»** и справа выбрать панель **«Отладочные сообщения»**.
2. Показать верхнюю ветку `Каждые 5 секунд → Случайная температура 20–35 °C → Опубликовать температуру`. Inject автоматически запускает поток каждые 5 секунд; его можно дополнительно нажать вручную.
3. Объяснить Function: `Math.random()` создаёт случайное значение, формула переводит его в диапазон 20–35 °C, а `Number(...toFixed(1))` оставляет один знак после запятой и записывает число в `msg.payload`. В `msg.topic` записывается `student/Sandrakula/lab2/temperature`.
4. Показать MQTT Out **«Опубликовать температуру»**. Эта нода отправляет сообщение публичному брокеру `broker.hivemq.com` на порт `1883`. Под нодой должно быть зелёное состояние **«подключен»**.
5. Показать нижнюю ветку `Получить температуру → Полученное MQTT-сообщение`. MQTT In подписывается на тот же топик и получает сообщения, которые брокер доставляет подписчикам. Под MQTT In также должно быть состояние **«подключен»**.
6. В панели Debug показать несколько последовательных объектов. Проверить, что новые сообщения появляются примерно каждые 5 секунд, `payload` является числом, а topic равен `student/Sandrakula/lab2/temperature`.
7. Простое объяснение MQTT: публичный брокер работает как посредник или «почтовое отделение». MQTT Out публикует сообщение по адресу-топику, а MQTT In получает всё, что приходит на этот топик. Публичный брокер доступен через интернет многим пользователям, поэтому в него нельзя отправлять пароли и другие секреты.
8. Отличие от HTTP: в HTTP клиент обычно сам отправляет запрос конкретному серверу и ждёт ответ. В MQTT издатель и подписчик напрямую друг друга не знают; они обмениваются сообщениями через брокер, а подписчик получает новые данные автоматически.

Для готового подтверждения показать [07-mqtt.png](../screenshots/07-mqtt.png): на нём видны обе ветки, подключённые MQTT-ноды и три реально полученных сообщения.

## Задание 2.8 — GET-эндпоинты

1. Открыть вкладку **«2.8 — GET Endpoints»**. Показать три отдельные цепочки: `/api/text`, `/api/info` и `/api/items`.
2. Объяснить общую схему: HTTP In принимает входящий GET-запрос, Function готовит тело, заголовки и статус, HTTP Response возвращает результат браузеру.
3. Для текстового ответа открыть `http://localhost:1880/api/text`. Показать строку `Hello from Sandrakula! Node-RED Lab 2.` и объяснить, что сервер возвращает статус 200 и тип `text/plain`.
4. Для JSON открыть `http://localhost:1880/api/info`. Показать два поля: `student` и `lab`. Ответ имеет статус 200 и тип `application/json`.
5. Для успешного поиска открыть `http://localhost:1880/api/items?id=1`. Показать объект Notebook и статус 200.
6. Для ошибки клиента открыть `http://localhost:1880/api/items?id=abc`. Function видит, что значение не является положительным целым числом, и возвращает `{"error":"Invalid item id"}` со статусом 400.
7. Для отсутствующего параметра можно открыть `http://localhost:1880/api/items`: ответ `{"error":"Missing item id"}` также имеет статус 400.
8. Для ненайденного элемента открыть `http://localhost:1880/api/items?id=999`. Число корректное, но такого элемента нет, поэтому возвращается `{"error":"Item not found"}` со статусом 404.
9. Если преподаватель просит доказать статусы, выполнить в PowerShell команды из [api.md](api.md) с ключом `-i`: `curl.exe` покажет первую строку `HTTP/1.1 200`, `400` или `404`.
10. Query parameter — это часть после знака `?`, например `id=1` в `/api/items?id=1`. Он передаёт дополнительное значение одному и тому же маршруту `/api/items`. Это отличается от части URL-пути: путь определяет сам маршрут, например `/api/items/1` был бы другим адресом.

Скриншот полной вкладки: [08-endpoints-flow.png](../screenshots/08-endpoints-flow.png). Скриншоты ответов находятся рядом и начинаются с `08-api-`.
